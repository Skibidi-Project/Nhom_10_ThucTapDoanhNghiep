# US-16/19 and main US-24/26: migration review

Review only. No production migration is authorized by this document. Do not start this branch against `products_db`: startup currently calls `Base.metadata.create_all` and `ensure_*` functions that can create tables or execute ALTERs, including `payments.note`, tenant, room, user and contract fields. US-26 adds `expenses`. Inventory actual columns, keys, constraints and engine before agreeing a release sequence; no live production schema comparison was performed here.

`us19_reading_revisions.sql` creates a table with `IF NOT EXISTS` for repeatable invocation, but this does not validate an existing table. Before and after applying it on a clone, compare `SHOW CREATE TABLE reading_revisions` with the reviewed SQL, verify InnoDB, PK, version type/nullability and FK target. Reject incompatible pre-existing tables. Existing readings without a revision are treated as revision 0; the first edit creates version 1. All concurrent app instances and direct writers must honor the room lock and revision protocol before rollout.

`us16_settlement_trial.sql` is **only for isolated testing**. Do not deploy the trial tables or enable the trial flag in production. Financial policy, final-period accounting, state lifecycle and production schema require a separate approval and migration. Its CREATE statements intentionally fail if a trial table exists instead of silently accepting an unknown schema.

The trial migration includes final-period approvals, meter handover references and refund method/reference. An isolated-only endpoint can consume manually approved amounts to issue a test invoice. Current inputs are review context, not proof of historical prices. See `FINAL_PERIOD_DESIGN_REVIEW.md` for unresolved input-versioning, meter replacement and adjustment requirements.

`us22_invoice_snapshots.sql` is a new review-only migration. Invoice issuance in this worktree fails closed and rolls back if this table is absent: production deployment must be coordinated with migration approval and compatible permissions. It contains a JSON representation and digest keyed to an existing invoice; MySQL triggers reject update and delete. This does not prevent a privileged administrator from disabling triggers or modifying schema; use least-privilege database accounts, audit, and reviewed incident procedures. Test privilege requirements for creating triggers and replicating DDL on a schema clone. Migration is not idempotent: an existing table or trigger must be compared and resolved manually, never silently accepted. MySQL DDL can partially commit, so inspect each object if interrupted.

No historical snapshots are fabricated. A legacy invoice returns `manual_review_required` and existing payment APIs remain usable. New evidence can also require manual review when readings are absent. There is no adjustment workflow yet; do not change a published snapshot or historic invoice to correct one. US-16 trial review records bind reviewer and timestamp to the snapshot digest. The isolated trial can use separately approved manual amounts for a mid-month final invoice; it does not infer a daily or full-month formula. Prior invoices still require complete reviewed snapshots. Three US-16 rules remain approved only for trial.

Before any approved production operation: make a consistent tested backup including schema, data, triggers and grants, verify a restore on an isolated server, record application/database versions and a rollback point, quiesce writers and inventory schema drift. Validate MySQL DDL and collation/FK compatibility in an isolated copy and get sign-off for both US-19 and upstream US-24/26 changes. Never depend on MySQL DDL being transactionally rolled back.

Rollback: stop writes and revert the application using an approved deployment procedure; preserve any new data. Reconcile any revisions or payments created since the backup before choosing a forward fix or restoring the verified backup. Dropping a revision table loses concurrency history and must not be used as an automatic rollback. Assess session/token invalidation if JWT keys are rotated. Test the procedure on the isolated copy first; any destructive production operation requires a separate explicit authorization.

Set a unique, unpredictable `JWT_SECRET` of at least 32 bytes via the deployment's secret manager or process environment. The integrated app fails before database initialization when absent or too short. Keep secrets out of Git and test logs.
